# 三、前后端接口契约

> 这份文档是前后端的**唯一约定源**。改接口先改这里，两边再动代码。
> 所有字段名、类型、状态码以本文为准。

---

## 1. 总览

| 方法 | 路径 | 用途 | 调用方 |
|---|---|---|---|
| POST | `/api/chat/stream` | 流式对话（SSE） | 聊天页 |
| GET | `/api/sessions` | 会话列表 | 聊天页侧边栏 |
| GET | `/api/sessions/{thread_id}/messages` | 历史消息 | 切换会话时 |
| DELETE | `/api/sessions/{thread_id}` | 删除会话 | 侧边栏 |
| GET | `/api/approvals` | 待审/已审列表 | 审批台 |
| POST | `/api/approvals/{apply_id}/decision` | 审批决策 | 审批台 |
| GET | `/api/traces/{thread_id}` | 调用链 | Trace 页 |
| GET | `/api/members/{member_id}` | 会员信息（调试用） | Trace 页 |

**统一约定**：

- 所有路径前缀 `/api`
- 除 `/chat/stream` 外全部返回 JSON
- 错误统一结构（见第 6 节）
- 时间一律 ISO 8601 UTC 字符串：`2026-11-06T09:30:00Z`
- 金额一律**整数分**（`9900` 表示 99.00 元），避免浮点误差

## 2. POST /api/chat/stream —— 流式对话

### 2.1 请求

```
POST /api/chat/stream
Content-Type: application/json
Accept: text/event-stream
```

```json
{
  "thread_id": "t-20261106-001",
  "content": "我要退款，订单 O20261106002"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `thread_id` | string | 是 | 会话 ID。新会话由前端生成（`crypto.randomUUID()`） |
| `content` | string | 是 | 用户输入，1-2000 字符 |

### 2.2 响应：SSE 流

响应头：

```
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no
```

帧序列（**顺序有约束**）：

```
data: {"type":"start","messageId":"m-001"}

data: {"type":"data-node","data":{"name":"classify","status":"done","intent":"change_request"}}

data: {"type":"text-start","id":"t-1"}

data: {"type":"text-delta","id":"t-1","delta":"好的，"}

data: {"type":"text-delta","id":"t-1","delta":"我帮您查一下订单状态。"}

data: {"type":"text-end","id":"t-1"}

data: {"type":"data-node","data":{"name":"refund_approval","status":"running"}}

data: {"type":"data-approval","data":{"apply_id":"AP20261106001","amount":9900,"summary":"退款申请：订单 O20261106002，金额 99.00 元","expires_at":"2026-11-07T09:30:00Z"}}

data: {"type":"finish"}

data: [DONE]
```

**没有中断（正常对话）时的收尾帧**：

```
data: {"type":"data-answer","data":{"text":"订单 ORD20260002 状态：已退款（REFUNDED），金额 49.00 元，下单时间 2026-09-10T05:33:00+08:00。","degraded":false,"citations":[],"intent":"order_status"}}

data: {"type":"finish"}

data: [DONE]
```

### 2.3 帧类型完整表

| type | 字段 | 何时发 | 前端怎么处理 |
|---|---|---|---|
| `start` | `messageId` | 流开始，**必发一次** | 初始化消息对象 |
| `text-start` | `id` | 一段文本开始 | 建立文本块 |
| `text-delta` | `id`, `delta` | 每个 token | 追加渲染 |
| `text-end` | `id` | 一段文本结束 | 收尾 |
| `data-node` | `data.name`, `data.status`, `data.intent?` | 节点进入/离开 | `<ThoughtChain>` 显示进度 |
| `data-approval` | `data.apply_id`, `data.amount`, `data.summary`, `data.expires_at` | 触发 HITL | 弹审批卡片，禁用输入框 |
| `data-answer` | `data.text`, `data.degraded`, `data.citations[]`, `data.intent` | 正常收尾时（无中断），`text-end` 之后、`finish` 之前 | **用 `data.text` 覆盖最后一条助手消息** |
| `error` | `errorText` | 任何异常 | `message.error` + 允许重试 |
| `finish` | 无 | 流结束，**必发一次** | `status` 转 idle |

**为什么需要 `data-answer`（不是冗余）**：

流式 `text-delta` 只是"过程观感"，节点生成完还会过一遍**后置校验**：

- 权益回答的引用 / 数字校验不过 → 整段换成「帮您转接人工」
- 订单回答的状态 / 日期 / 金额与工具结果对不上 → 整段换成工具原文
- 检索门限没过、模型没调工具 → 根本没有 LLM 输出，回答是纯代码拼的

这三种情况里，前端已经从 `text-delta` 收到了**错误内容**。只认流式文本的话，用户看到的和数据库里的事实是两回事——这正是订单节点最初把时间、金额、状态三项全说错的形态。所以收尾必须有一帧"权威版本"。

另外 `data.degraded=true` 表示本轮走了降级/转人工，前端可以打个「已转人工」标签。

**约束**（写错前端就不正常，实测得出）：

1. `start` 必须第一个发，且带 `messageId`
2. `finish` 必须最后一个发（`[DONE]` 之前）。少了它 `status` 永远停在 `streaming`
3. `text-start` / `text-end` 必须成对，中间的 `text-delta` 的 `id` 要一致
4. 自定义数据帧的 `type` 必须是 `data-<name>` 格式，否则客户端 schema 校验失败直接抛错
5. **中断场景没有 `data-answer`**（回答还没生成完，要等审批后 resume），此时以 `data-approval` 为准

### 2.4 心跳

服务端每 15 秒发一行 SSE 注释：

```
: ping - 2026-11-06 09:30:15
```

后端用 `EventSourceResponse(gen(), ping=15)` 自动处理。前端不需要做任何事——`eventsource-parser` 会忽略注释行。

**为什么必须有**：公司网关 / nginx 默认 60 秒无数据断连。LLM 首字延迟可能超过 30 秒（复杂推理场景），没心跳会断在第一个字之前。

### 2.5 客户端断开

前端调 `stop()` 或关闭页面 → TCP 断开 → 后端 `request.is_disconnected()` 返回 True → 停止图执行，不再调 LLM。

**这条很重要**：不做这个，用户点"停止"后模型还在后台跑完，token 照烧。

## 3. GET /api/approvals —— 审批列表

### 3.1 请求

```
GET /api/approvals?status=pending&page=1&page_size=20
```

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `status` | string | `pending` | `pending` / `approved` / `rejected` / `expired` / `all` |
| `page` | int | 1 | 从 1 开始 |
| `page_size` | int | 20 | 最大 100 |

### 3.2 响应

```json
{
  "items": [
    {
      "apply_id": "AP20261106001",
      "thread_id": "t-20261106-001",
      "member_id": "M10023",
      "type": "refund",
      "amount": 9900,
      "reason": "用户申请退款，订单状态 EFFECTIVE",
      "status": "pending",
      "created_at": "2026-11-06T09:30:00Z",
      "expires_at": "2026-11-07T09:30:00Z",
      "summary": "退款申请：订单 O20261106002，金额 99.00 元"
    }
  ],
  "total": 12,
  "page": 1,
  "page_size": 20
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `items[].apply_id` | string | 审批单号 |
| `items[].thread_id` | string | 对应会话，审批后要恢复这个会话的图 |
| `items[].type` | string | `refund` / `reissue` |
| `items[].amount` | int | **整数分**，前端自己除 100 |
| `items[].status` | string | 见上 |
| `items[].expires_at` | string | 超时自动作废的时间点 |
| `items[].summary` | string | 给审批人看的一句话摘要，由后端生成 |

**为什么后端返回 `summary` 而不是前端拼**：
摘要是给审批人做判断的依据，措辞要准确（金额、订单号、原因）。这属于业务逻辑，不该让前端猜格式。

## 4. POST /api/approvals/{apply_id}/decision —— 审批决策

### 4.1 请求

```
POST /api/approvals/AP20261106001/decision
Content-Type: application/json
```

```json
{
  "approved": true,
  "reviewer": "张主管",
  "comment": "同意，金额在权限范围内"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `approved` | boolean | 是 | true 同意 / false 驳回 |
| `reviewer` | string | 是 | 审批人，1-32 字符 |
| `comment` | string | 是（驳回时） | 驳回必须填理由，同意可空，最长 200 字符 |

### 4.2 响应

**成功 200**：

```json
{
  "ok": true,
  "apply_id": "AP20261106001",
  "status": "approved",
  "decided_at": "2026-11-06T10:15:00Z"
}
```

**已被处理 409**：

```json
{
  "error_no": 40901,
  "error_msg": "该申请已处理或已过期"
}
```

**为什么是 409 不是 400**：
409 Conflict 表达"请求合法，但与当前资源状态冲突"。两个人同时点审批，后点的必然撞上这个，前端应该提示"已被 XXX 处理"并刷新列表。

### 4.3 后端处理顺序（不能颠倒）

```
1. CAS 更新审批单：WHERE status='pending' AND expires_at > now
   ├─ rowcount == 0 → 返回 409，结束
   └─ rowcount == 1 → 继续
2. 恢复 LangGraph：graph.ainvoke(Command(resume=...), thread_id)
3. 返回 200
```

**先 CAS 再 resume**。反过来的话，两个并发请求会都通过检查、都 resume，图执行两遍，退款两次。

### 4.4 前端必须做的事

审批成功后：

1. 从列表移除该项（或改为已处理态）
2. 如果当前聊天页正等着这个 `apply_id`，**重新拉一次会话历史**或提示用户"审批已完成，点击继续"

第 2 点容易漏。审批台和聊天页是两个页面，用户可能在审批台点了同意，聊天页那边还挂着"等待审批"的卡片。

## 5. 会话相关接口

### 5.1 GET /api/sessions

```
GET /api/sessions?page=1&page_size=20
```

```json
{
  "items": [
    {
      "thread_id": "t-20261106-001",
      "member_id": "M10023",
      "title": "退款咨询",
      "last_message": "退款已提交，预计 1-3 个工作日到账。",
      "message_count": 8,
      "has_pending_approval": false,
      "updated_at": "2026-11-06T09:35:00Z"
    }
  ],
  "total": 3
}
```

`title` 取首条用户消息前 20 字，后端生成。`has_pending_approval` 用于在侧边栏打标记。

### 5.2 GET /api/sessions/{thread_id}/messages

```json
{
  "thread_id": "t-20261106-001",
  "messages": [
    { "id": "m-001", "role": "user", "content": "我要退款", "created_at": "..." },
    { "id": "m-002", "role": "assistant", "content": "好的，我帮您查一下", "created_at": "..." }
  ]
}
```

**注意**：历史消息只返回纯文本，不返回当时的 `data-node` / `data-approval` 帧。工具调用链走 `/api/traces/{thread_id}` 单独拉。

**为什么**：历史里的审批卡片是**当时**的状态，现在早就变了。重新渲染旧卡片会误导用户以为还能点。

### 5.3 DELETE /api/sessions/{thread_id}

```json
{ "ok": true }
```

删除会话 = 删 checkpoints 里这个 `thread_id` 的所有记录 + 会话元数据。**不删审批单**（审批是业务记录，不能因为删会话就没了）。

## 6. 错误结构

### 6.1 统一格式

所有非 SSE 接口的错误：

```json
{
  "error_no": 40001,
  "error_msg": "thread_id 不能为空",
  "detail": null
}
```

| 字段 | 说明 |
|---|---|
| `error_no` | 业务错误码，前三位是 HTTP 状态，后两位是细分 |
| `error_msg` | 可以直接展示给用户的中文 |
| `detail` | 调试信息，**生产环境为 null**（不泄露内部实现） |

### 6.2 错误码

| error_no | HTTP | 场景 |
|---|---|---|
| 40001 | 400 | 参数校验失败 |
| 40401 | 404 | 会话 / 审批单不存在 |
| 40901 | 409 | 审批单已被处理 |
| 40902 | 409 | 审批单已过期 |
| 42201 | 422 | 语义错误（如驳回未填理由） |
| 50001 | 500 | 服务内部错误 |
| 50201 | 502 | LLM 服务不可用 |

### 6.3 SSE 流里的错误

流已经开始后出错，**不能改 HTTP 状态码**（头已经发出去了）。用 `error` 帧：

```
data: {"type":"error","errorText":"模型服务暂时不可用，请稍后重试"}
```

前端 `useChat` 的 `onError` 会收到。**不要发完 error 就断连**，正常发 `finish` 收尾，否则前端状态卡住。

## 7. 前端类型定义

`web/src/types/api.ts`，与本文一一对应：

```ts
export interface ChatRequest {
  thread_id: string;
  content: string;
}

export type ApprovalStatus = 'pending' | 'approved' | 'rejected' | 'expired';
export type ApprovalType = 'refund' | 'reissue';

export interface ApprovalItem {
  apply_id: string;
  thread_id: string;
  member_id: string;
  type: ApprovalType;
  amount: number;          // 整数分
  reason: string;
  status: ApprovalStatus;
  created_at: string;
  expires_at: string;
  summary: string;
}

export interface ApprovalListResp {
  items: ApprovalItem[];
  total: number;
  page: number;
  page_size: number;
}

export interface DecisionReq {
  approved: boolean;
  reviewer: string;
  comment: string;
}

export interface SessionItem {
  thread_id: string;
  member_id: string;
  title: string;
  last_message: string;
  message_count: number;
  has_pending_approval: boolean;
  updated_at: string;
}

export interface ApiError {
  error_no: number;
  error_msg: string;
  detail: string | null;
}
```

`web/src/types/chat.ts`：

```ts
import type { UIMessage } from 'ai';

export type MyDataParts = {
  node: { name: string; status: 'running' | 'done'; intent?: string };
  approval: { apply_id: string; amount: number; summary: string; expires_at: string };
  /** 权威答复：覆盖流式文本（可能被后置校验改写，也可能是纯代码生成） */
  answer: {
    text: string;
    degraded: boolean;
    citations: { code: string; name: string }[];
    intent?: string | null;
  };
};

export type MyUIMessage = UIMessage<unknown, MyDataParts>;
```

**`MyDataParts` 的 key 必须和 `data-<name>` 里的 `<name>` 完全一致**。写成 `node` 对应 `data-node`，写成 `approval` 对应 `data-approval`。写错的话 `onData` 里 `part.data` 是 `unknown`，TS 不报错但运行时拿不到字段。

## 8. 联调检查清单

前后端第一次对接时按顺序过一遍，能省掉大部分来回：

- [ ] 后端能返回 `start` 帧，`messageId` 非空
- [ ] 逐字输出正常，不是一次性刷完（说明没被 nginx/中间层缓冲）
- [ ] 流结束有 `finish` 帧，前端输入框恢复可用
- [ ] 点"停止"按钮，后端日志显示图执行中止（不是跑完才停）
- [ ] 触发审批时，`data-approval` 帧被 `onData` 收到，卡片弹出
- [ ] 正常对话结束时收到 `data-answer`，界面显示的是这一帧的 `text`（不是流式残留）
- [ ] 审批台点同意后返回 200，再点一次返回 409
- [ ] 并发点两次同意，恰好一个 200、一个 409（不是两个都 200）
- [ ] 断开网络，前端显示可读的错误提示，不是白屏
- [ ] 15 秒无输出时连接不断（可把 LLM 调成慢速或用 mock 验证）

## 9. 版本与兼容

| 项 | 规则 |
|---|---|
| 路径版本 | 当前不加 `/v1`。简历项目无外部调用方，加了是过度设计 |
| 破坏性变更 | 只在本文件记录，不留兼容层 |
| 帧类型新增 | 前端默认忽略未知 `type`（AI SDK 的 `looseObject` 容忍额外字段），所以**加新帧不破坏旧前端** |
| 字段删除 | 视为破坏性变更，必须同步改这里 |
