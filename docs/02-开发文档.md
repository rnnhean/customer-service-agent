### 分层原则（改代码时最容易违反的）

| 层 | 允许做 | 禁止做 |
|---|---|---|
| `api/` | 解析请求、调 graph、序列化响应 | 写 SQL、写提示词、调 LLM |
| `graph/` | 状态流转、调工具、拼提示词 | 直接 `import fastapi`、直接连数据库 |
| `tools/` | 参数校验、调 repo、返回结构化结果 | 拼提示词、知道 HTTP 存在 |
| `db/` | SQL、事务 | 知道 Agent 存在 |

**为什么强调这个**：`tools/` 是要被 LLM 调用的，它必须能被独立测试（不启 HTTP、不启 LLM）。`graph/` 要被 LangGraph 序列化状态，它不能持有数据库连接之类的不可序列化对象。

## 3. 数据层

### 3.1 建表

`db/schema.sql`，七张业务表。**时间一律 `timestamptz`，JSON 一律 `jsonb`**——这两条是 PG 相对 SQLite 最直接的红利：

```sql
CREATE TABLE IF NOT EXISTS members (
  member_id   TEXT PRIMARY KEY,
  level       TEXT NOT NULL,          -- normal / silver / gold / platinum
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS member_status (
  member_id    TEXT PRIMARY KEY REFERENCES members(member_id),
  status       TEXT NOT NULL,         -- inactive / active / expired / canceling
  effective_at timestamptz,
  expire_at    timestamptz,
  auto_renew   boolean DEFAULT false
);

CREATE TABLE IF NOT EXISTS benefits (
  code        TEXT PRIMARY KEY,
  level       TEXT NOT NULL,
  name        TEXT NOT NULL,
  value       TEXT,
  stackable   boolean DEFAULT false,  -- 能否与其它权益叠加
  expire_days INTEGER
);

CREATE TABLE IF NOT EXISTS orders (
  order_id    TEXT PRIMARY KEY,
  member_id   TEXT NOT NULL REFERENCES members(member_id),
  type        TEXT NOT NULL,          -- open / renew / refund
  status      TEXT NOT NULL,          -- PENDING / EFFECTIVE / REFUNDING / REFUNDED / CLOSED
  amount      INTEGER NOT NULL,       -- 分
  created_at  timestamptz NOT NULL,
  updated_at  timestamptz NOT NULL
);

CREATE TABLE IF NOT EXISTS approvals (
  apply_id    TEXT PRIMARY KEY,
  thread_id   TEXT NOT NULL,          -- 关联 LangGraph 现场，恢复时要用
  member_id   TEXT NOT NULL REFERENCES members(member_id),
  type        TEXT NOT NULL,          -- refund / reissue
  amount      INTEGER,
  reason      TEXT,
  status      TEXT NOT NULL,          -- pending / approved / rejected / expired
  version     INTEGER NOT NULL DEFAULT 0,   -- CAS 防重复审批
  reviewer    TEXT,
  comment     TEXT,                   -- 审批意见，驳回时必填
  created_at  timestamptz NOT NULL,
  decided_at  timestamptz,
  expires_at  timestamptz NOT NULL
);

CREATE TABLE IF NOT EXISTS complaints (
  ticket_id    TEXT PRIMARY KEY,
  member_id    TEXT NOT NULL REFERENCES members(member_id),
  category     TEXT NOT NULL,
  priority     INTEGER NOT NULL,
  sla_deadline timestamptz NOT NULL,
  status       TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS member_profile (
  member_id   TEXT PRIMARY KEY REFERENCES members(member_id),
  profile     jsonb NOT NULL,         -- 偏好、历史诉求、沟通风格
  updated_at  timestamptz NOT NULL
);

-- 索引：客服场景高频查询
CREATE INDEX IF NOT EXISTS idx_orders_member ON orders(member_id);
CREATE INDEX IF NOT EXISTS idx_approvals_status ON approvals(status, created_at);
CREATE INDEX IF NOT EXISTS idx_complaints_member ON complaints(member_id);
-- 低频字段用 GIN，别每列都建 B-tree
CREATE INDEX IF NOT EXISTS idx_member_profile_gin ON member_profile USING gin (profile);
```

**LangGraph 的 checkpoint 表不用手写**，`AsyncPostgresSaver.setup()` 会自动建。

> 注意 `CREATE TABLE IF NOT EXISTS` **不会给已存在的表加列**。改表结构时要么写 `ALTER TABLE ... ADD COLUMN`，要么在开发期直接 `docker compose down -v` 重建。生产环境走迁移脚本（Alembic 或手写 SQL），不要靠 ORM 自动同步。

### 3.2 造数据

`db/seed.py` 生成：

| 表 | 数量 | 说明 |
|---|---|---|
| members | 200 | 四个等级均匀分布 |
| member_status | 200 | active 60% / expired 25% / canceling 10% / inactive 5% |
| benefits | 40 | 每等级 10 条权益规则，**文案用真实中文** |
| orders | 400 | 每个会员 0-3 单，状态覆盖全部枚举 |

| complaints | 30 | 覆盖不同 category 和 SLA 紧急度 |

**为什么要 200 个会员而不是 3 个**：
调试分页、筛选、"查不到"的边界路径时，3 条数据永远测不出问题。而且演示时随机挑一个会员 ID 提问，比总问同一个更像真的。

**造数据的随机必须固定种子**：

```python
rng = random.Random(20261106)   # 固定种子，每次跑出来的数据一样
```

否则你改完代码重跑 seed，订单状态全变了，之前的测试用例全废。

### 3.4 CAS 更新审批（防重复审批的关键）

两个人同时点"同意"，或者用户狂点两次，不能执行两次退款。

```python
async def cas_update_approval(
    apply_id: str, approved: bool, reviewer: str, comment: str,
) -> dict | None:
    """只有从 pending 成功迁移到终态的那一次返回记录，其余返回 None。"""
    now = datetime.now(UTC)
    async with get_conn() as conn:          # 连接池借出
        async with conn.cursor() as cur:
            await cur.execute(
                """
                UPDATE approvals
                   SET status = %s, reviewer = %s, comment = %s,
                       decided_at = %s, version = version + 1
                 WHERE apply_id = %s AND status = 'pending' AND expires_at > %s
                """,
                ("approved" if approved else "rejected", reviewer, comment, now, apply_id, now),
            )
            if cur.rowcount == 0:
                await conn.rollback()
                return None            # 已被处理 / 已过期
            await conn.commit()
        return await _fetch_approval(conn, apply_id)
```

**面试点**：这是乐观锁（`WHERE status='pending'` 做条件更新 + `rowcount` 判定），不是悲观锁。在 PostgreSQL 上，这条 UPDATE 会对目标行加行级排他锁：**两个并发事务里只有一个 `rowcount == 1`，另一个阻塞到前者提交后看到 `status` 已变，`rowcount == 0`**。这才是它真正被验证的地方——SQLite 单写者下你测不出这个结论。

**为什么不用 `SELECT ... FOR UPDATE`**：也能防重复，但要两轮往返（锁行 → 判断 → 更新），而且应用层还得自己处理锁等待超时。条件更新一条语句完成"检查 + 变更"，语义更紧。

## 4. Agent 编排层

### 4.1 状态定义

`graph/state.py`：

```python
from typing import Annotated, Literal, TypedDict
from langchain_core.messages import AnyMessage
from langgraph.graph.message import add_messages

Intent = Literal["benefit_qa", "order_status", "change_request", "complaint", "unknown"]

class AgentState(TypedDict, total=False):
    messages: Annotated[list[AnyMessage], add_messages]
    thread_id: str
    member_id: str | None
    intent: Intent
    slots: dict[str, str]        # order_id / amount / reason
    route: str
    approval_id: str | None
    risk_level: Literal["low", "high"]
    citations: list[dict]        # 引用来源，防幻觉用
    error: str | None
```

**为什么 `total=False`**：LangGraph 的 state 是增量合并的，不是每个节点都要返回全部字段。用 `TypedDict` 全必填会导致每个节点都得写一堆 `None`。

**为什么 `messages` 用 `add_messages`**：它会做 message id 去重 + 增量追加。不写这个 reducer，节点返回的消息会覆盖而不是追加。

### 4.2 图构建

`graph/build.py`：

```python
from langgraph.graph import StateGraph, START, END

def build_graph(checkpointer=None):
    # 四个独立 Agent：各自的提示词、工具集、推理循环
    benefit_agent   = create_agent(LLM, tools=BENEFIT_TOOLS,   system_prompt=BENEFIT_PROMPT)
    order_agent     = create_agent(LLM, tools=ORDER_TOOLS,     system_prompt=ORDER_PROMPT)
    refund_agent    = create_agent(LLM, tools=REFUND_TOOLS,    system_prompt=REFUND_PROMPT,
                                   middleware=[SummarizationMiddleware(
                                       model=LLM, trigger=("messages", 20), keep=("messages", 6),
                                   )])
    complaint_agent = create_agent(LLM, tools=COMPLAINT_TOOLS, system_prompt=COMPLAINT_PROMPT)

    g = StateGraph(AgentState)
    g.add_node("classify", classify_node)
    g.add_node("benefit_rag", benefit_agent)
    g.add_node("order_flow", order_agent)
    g.add_node("refund_approval", refund_agent)
    g.add_node("complaint", complaint_agent)
    g.add_node("clarify", clarify_node)
    g.add_node("finalize", finalize_node)

    g.add_edge(START, "classify")
    g.add_conditional_edges("classify", route_by_intent, {
        "benefit_qa": "benefit_rag",
        "order_status": "order_flow",
        "change_request": "refund_approval",
        "complaint": "complaint",
        "unknown": "clarify",
    })
    for n in ["benefit_rag", "order_flow", "refund_approval", "complaint", "clarify"]:
        g.add_edge(n, "finalize")
    g.add_edge("finalize", END)

    return g.compile(checkpointer=checkpointer)
```

**注意 1**：子图（`create_agent` 的产物）默认用自己的 `AgentState`，父图的 `AgentState` 字段不会自动流进去。需要 `state_schema=AgentState` 才能共享。这一点在 P1 阶段必须验证，否则会出现"父图有 member_id，子图看不到"。

**注意 2（重要，别踩坑）**：审批流程**不用** `HumanInTheLoopMiddleware`，而是自己写 `interrupt()`（见 4.4）。

原因：`HumanInTheLoopMiddleware` 是在**单个 tool call 层面**中断——它暂停的是"执行 `do_refund` 这个工具"，恢复后直接执行工具。但我们的业务要求是：

- 中断时要**先落一条 `approvals` 记录**，审批台才有东西可看
- 恢复时要**重查订单状态**，不能信任中断时的快照
- 恢复后要**可能直接返回消息**而不是执行工具

这三件事 middleware 做不了。middleware 适合"工具调用前弹个确认框"这种简单场景，不适合"跨系统的业务审批流"。自己写 `interrupt()` 才能控制前后逻辑。

### 4.3 路由

`classify` 节点用 `with_structured_output` 一次拿到 `intent` + 抽取的槽位：

```python
class Route(BaseModel):
    intent: Intent
    order_id: str | None = None
    reason: str | None = None
    confidence: float

async def classify_node(state: AgentState) -> dict:
    llm = LLM.with_structured_output(Route)
    try:
        r = await llm.ainvoke([
            SystemMessage(CLASSIFY_PROMPT),
            *state["messages"][-6:],      # 只带最近 6 条，控成本
        ])
    except Exception:
        return {"intent": "unknown", "error": "classify_failed"}
    if r.confidence < 0.6:
        return {"intent": "unknown"}       # 低置信度走澄清，不硬猜
    return {"intent": r.intent, "slots": {k: v for k, v in r.model_dump().items()
                                          if k in ("order_id", "reason") and v}}
```

**为什么低置信度走 clarify 而不是默认兜底**：
客服场景猜错的代价远高于多问一句。猜错意图 → 用户要重新说一遍，体验更差。

### 4.4 HITL（人工审批）

这是本项目最核心的差异化能力。

```python
# graph/nodes/refund.py
async def refund_node(state: AgentState) -> dict:
    # 1) 先落一条 pending 审批单，拿到 apply_id
    apply = await create_approval(
        thread_id=state["thread_id"],
        member_id=state["member_id"],
        amount=state["slots"]["amount"],
        expires_at=now_plus(hours=24),
    )
    # 2) 中断，把现场交给人工
    decision = interrupt({
        "type": "approval_required",
        "apply_id": apply["apply_id"],
        "summary": build_approval_summary(state),
    })
    # ---- 以下只有 resume 之后才执行 ----
    if not decision.get("approved"):
        return {"messages": [AIMessage(f"您的申请已被驳回：{decision.get('comment', '')}")]}

    # 3) 恢复后必须重查：人工审批可能隔了几小时，订单状态早就变了
    order = await get_order(state["slots"]["order_id"])
    if not order or order["status"] != "EFFECTIVE":
        return {"messages": [AIMessage("订单状态已变化，需重新提交申请。")]}

    await do_refund(apply["apply_id"])
    return {"messages": [AIMessage("退款已提交，预计 1-3 个工作日到账。")]}
```

**恢复接口**：

```python
# api/approvals.py
@router.post("/{apply_id}/decision")
async def decide(apply_id: str, body: DecisionBody):
    # CAS 先落库，抢不到就是重复提交
    apply = await cas_update_approval(apply_id, body.approved, body.reviewer, body.comment)
    if apply is None:
        raise HTTPException(409, "该申请已处理或已过期")

    # 再恢复图
    await graph.ainvoke(
        Command(resume={"approved": body.approved, "comment": body.comment}),
        config={"configurable": {"thread_id": apply["thread_id"]}},
    )
    return {"ok": True}
```

**顺序很重要**：先 CAS 再 resume。
反过来会有竞态——两个请求同时通过 CAS 检查，然后都 resume，图跑两次，退款两次。

### 4.5 为什么 HITL 不能只用 `interrupt`

`interrupt()` 只负责"暂停"。完整闭环还差三件事：

| 问题 | 解法 |
|---|---|
| 进程重启了，谁在等审批？ | checkpoint 落 PostgreSQL，`thread_id` 存在业务表里，多实例都能接着跑 |
| 用户关页面了，图一直挂着？ | `expires_at` 超时作废，后台定时任务扫 |
| 重复点审批按钮？ | CAS 条件更新 |
| 审批通过后数据变了？ | resume 后**重查**，不信任中断时的快照 |

这四条加起来才叫 HITL，"用了 `interrupt()`" 只是第一步。

## 5. 流式输出

### 5.1 后端吐帧

关键决策：**用 AI SDK 的协议，不用自定义 SSE**。

原因：自定义协议前端要手写解析、增量拼接、错误处理；用 AI SDK 协议前端 `useChat` 直接吃。

协议要求（从 `ai@7.0.163` 源码 `src/ui-message-stream/ui-message-chunks.ts` + `@ai-sdk/provider-utils@5` 的 `parseJsonEventStream` 实测）：

```
响应头：
  content-type: text/event-stream
  cache-control: no-cache
  x-accel-buffering: no        # 关掉 nginx 缓冲，必须加

  （x-vercel-ai-ui-message-stream: v1 官方会带，但客户端不校验，可带可不带）

帧格式（SSE 的 data 字段里是 JSON，一行一个）：
  {"type":"start","messageId":"..."}
  {"type":"text-start","id":"t1"}
  {"type":"text-delta","id":"t1","delta":"您"}
  {"type":"text-delta","id":"t1","delta":"好"}
  {"type":"text-end","id":"t1"}
  {"type":"data-approval","data":{"apply_id":"AP...","amount":99}}
  {"type":"finish"}
  data: [DONE]                 （可选，客户端见到就停止解析）
```

**三个实测得到的硬性要求**（写错就是前端不显示或直接报错）：

1. **必须有 `start` 帧**，且带 `messageId`。客户端收到它才初始化消息对象。
2. **必须有 `finish` 帧**。少了它 `status` 会一直停在 `streaming`，输入框永远禁用。
3. **`text-*` 三帧必须成套**：`text-start` → 若干 `text-delta` → `text-end`，`id` 要一致。只发 `text-delta` 不发 start/end，部分版本会丢内容。

自定义数据用 **`data-<名字>`**，schema 校验规则是"`type` 必须以 `data-` 开头"，所以 `data-approval`、`data-node` 都合法，`event: approval` 不合法。

**与 `sse-starlette` 配合的注意点**：
`EventSourceResponse` 默认会把 dict 的 `event` 键渲染成 `event: xxx` 行。客户端解析器（`eventsource-parser`）只读 `data` 字段，`event:` 行不影响解析，可以留着。但**不要把协议内容放 `event:` 里**——那个字段客户端不看。

实现（`api/chat.py`）：

```python
@router.post("/stream")
async def chat_stream(req: ChatRequest, request: Request):
    async def gen():
        writer = ChunkWriter()          # 自写的薄封装，负责补 id / 加 start-finish
        async for chunk in writer.start():
            yield chunk

        config = {
            "configurable": {"thread_id": req.thread_id},
            "callbacks": [get_langfuse_handler()],
        }
        try:
            async for mode, data in graph.astream(
                {"messages": [HumanMessage(req.content)], "thread_id": req.thread_id},
                config,
                stream_mode=["messages", "updates"],
            ):
                if await request.is_disconnected():
                    return
                if mode == "messages":
                    msg, _meta = data
                    if isinstance(msg, AIMessageChunk) and msg.text:
                        yield writer.text(msg.text)
                else:
                    for node, update in data.items():
                        yield writer.data("node", {"name": node})
                        if update.get("approval_id"):
                            yield writer.data("approval", update)
        except Exception as e:
            yield writer.error(str(e))
        yield writer.finish()

    return EventSourceResponse(gen(), ping=15)   # ping=15 是心跳
```

**三件必须做的事**：

1. **心跳** `ping=15`：不加的话，超过网关空闲超时的连接会被掐断
2. **断连检测** `request.is_disconnected()`：用户关页面了就停止，不要继续烧 token
3. **异常兜底**：catch 后发 `error` 帧，别让连接裸断（前端会以为是网络问题）

## 6. 记忆与上下文

### 6.1 分三层，别混

| 层 | 存什么 | 存哪 | 生命周期 |
|---|---|---|---|
| 短期 | 最近 N 轮原文 | LangGraph checkpoint | 会话内 |
| 长期 | 用户偏好、历史诉求 | `member_profile` 表 | 跨会话 |
| 业务事实 | 订单状态、余额、权益 | 业务表 | 每次现查 |

**最重要的原则：业务事实不进记忆。**

订单状态会变。如果把它写进"长期记忆"，模型会拿三天前的状态回答今天的用户，而且是笃定的错。正确做法是每次都用工具查库。

能查的不用 LLM，能查的也不进记忆。

### 6.2 短期记忆

LangGraph 的 checkpointer 本身就是短期记忆——同一个 `thread_id` 下的 `messages` 自动累积。

但会无限增长。用 `SummarizationMiddleware` 控制：

```python
SummarizationMiddleware(
    model=LLM,
    trigger=("messages", 20),   # 超过 20 条开始摘要
    keep=("messages", 6),       # 保留最近 6 条原文
)
```

`trigger` / `keep` 支持三种单位（摘自 `langchain 1.4.9` 源码）：

| 形式 | 含义 |
|---|---|
| `("messages", 20)` | 按**条数** |
| `("tokens", 3000)` | 按 **token 数**（更准，但要 counter） |
| `("fraction", 0.5)` | 按模型上下文窗口的**比例**（默认是 `("fraction", 0.5)`） |

**本项目为什么用 `messages` 而不是 `tokens`**：
`tokens` 需要给模型传 tokenizer，国内模型不一定有对应实现，配错了数字误差很大。`messages` 口径粗暴但不会错，客服单轮问答长度可控，20 条够用。

### 6.3 长期记忆

只有满足条件才写：

```python
class MemoryWrite(BaseModel):
    should_write: bool
    kind: Literal["preference", "constraint", "history"] | None
    content: str | None
    reason: str
```

判定规则写在提示词里，几条硬约束：

- 一次性的诉求（"我这次要退款"）**不写**
- 订单号、金额、时间 **不写**（会过期）
- 稳定偏好（"我不喜欢电话回访"）、长期约束（"我是企业账户"）**写**

**注入时的措辞**（这条很关键）：

```
以下是该用户的历史背景，仅作参考。
凡涉及制度、权益、订单状态的，一律以本轮工具查询结果为准。
背景信息与查询结果冲突时，无条件以查询结果为准。
```

不写这句，模型会把记忆当事实，和查库结果打架时随机选一个。

## 7. 防幻觉

四道闸，从强到弱：

### 7.1 检索门限

```python
results = await search_benefits(query, top_k=5)
if not results or results[0]["score"] < settings.rag_min_score:
    return {"messages": [AIMessage("这个问题我暂时查不到，帮您转人工客服。")],
            "route": "handoff"}
```

宁可转人工，不要硬编。

### 7.2 强制引用

提示词里硬性要求：

```
回答权益类问题必须引用检索到的条款编号，格式：[权益-XXX]。
没有检索到对应条款时，直接说查不到，不得凭印象回答。
```

### 7.3 编号校验（后置检查）

```python
def validate_citations(answer: str, retrieved: list[dict]) -> bool:
    cited = set(re.findall(r"\[权益-([A-Z0-9]+)\]", answer))
    valid = {r["code"] for r in retrieved}
    return bool(cited) and cited <= valid     # 有引用 且 全部来自真实检索结果
```

模型编了一个不存在的编号 → 校验失败 → 重试一次或降级。

### 7.4 数字校验

回答里出现的金额、天数、比例，必须能在工具返回里找到：

```python
def validate_numbers(answer: str, tool_results: list[str]) -> bool:
    nums = re.findall(r"\d+(?:\.\d+)?", answer)
    corpus = " ".join(tool_results)
    return all(n in corpus for n in nums)
```

**这四道闸的意义不在"完全消除幻觉"**——消不掉。意义在于：**幻觉发生时能被检测到，并且有降级路径**。面试时讲这个比讲"我用 prompt 让它不要瞎编"有说服力。

## 8. 上下文预算

不是"超了就截断"，是**先算预算再组装**。

```python
BUDGET = {
    "system_prompt":   1500,
    "long_memory":      500,
    "retrieved_docs":  2500,
    "tool_schemas":    1200,
    "messages":        3000,
}
TOTAL = 8700     # 给模型 128k 留足余量，客服场景不需要更长

def assemble(state) -> list[BaseMessage]:
    msgs = [SystemMessage(build_system(state))]

    # 长期记忆：超预算就只留最近更新的
    mem = fit_budget(render_memory(state), BUDGET["long_memory"])
    if mem:
        msgs.append(SystemMessage(mem))

    # 检索结果：超预算按 score 从低往高丢
    docs = fit_budget_by_score(state["retrieved"], BUDGET["retrieved_docs"])
    if docs:
        msgs.append(SystemMessage(render_docs(docs)))

    # 对话历史：超预算从最旧的丢，但至少保留最近 4 条
    msgs.extend(trim_history(state["messages"], BUDGET["messages"], keep_min=4))
    return msgs
```

**为什么不是简单 `messages[-10:]`**：
一条用户消息可能带很长的订单列表，10 条能到 20k token；一条"好的"只占 2 token。按条数截是错的，按 token 截才对。

**裁剪优先级**（从先裁到后裁）：
1. 检索结果里 score 最低的
2. 最旧的对话历史（保底留 4 条）
3. 长期记忆里最老的条目
4. 系统提示词**永不裁**

## 11. 常见问题

### Q: 为什么子图看不到父图的 state？

`create_agent` 默认用自己的 `AgentState`。要在父图里共享字段，得显式传 `state_schema`。P1 阶段第一件事就是验证这个。

### Q: `interrupt()` 之后进程重启，还能恢复吗？

能。前提是 checkpointer 是持久化的（`AsyncPostgresSaver`，不是 `MemorySaver`）。恢复时用原 `thread_id` 调 `Command(resume=...)`。

### Q: 前端 `useChat` 收不到 `data-approval`？

两个可能：一是后端帧格式不对（必须是 `{"type":"data-approval","data":{...}}`，不是 `{"event":"approval"}`）；二是 `MyUIMessage` 没声明 `MyDataParts`，TS 推不出来。

### Q: PG 连接数打满 / 报 `too many clients`？

不要每个请求 `psycopg.AsyncConnection.connect()`，用连接池，并且把池上限压在企业 PG 的 `max_connections` 之下：

```python
pool = AsyncConnectionPool(settings.database_url, min_size=2, max_size=20, open=False)
await pool.open()
```

`AsyncPostgresSaver` **不能**复用业务池——它要求连接是 `autocommit=True` 的（LangGraph 自己管事务边界），而业务池是 `autocommit=False`（我们要能显式 `commit` / `rollback`）。所以实际上是**两个池**：

| 池 | 用途 | autocommit | 大小 |
|---|---|---|---|
| `csa-pool` | 业务表读写（orders / approvals / traces…） | `False` | 2–20 |
| `csa-checkpoint-pool` | LangGraph checkpointer | `True` | 1–5 |

这不是"连接数翻倍"的失控，是两套语义不同的连接。内网部署时按**两个池的上限之和**（默认 25）去核对 PG 的 `max_connections`，而不是按单个池算。

如果非想省连接，可以在 PG 前面挂 PgBouncer（transaction 模式），此时应用侧池上限可以放小，但要注意 `LISTEN/NOTIFY` 和 prepared statement 在 transaction pooling 下会出问题。

### Q: 多实例部署时 checkpoint 表冲突？

`AsyncPostgresSaver.setup()` 建表是幂等的，但**只能有一个实例在启动时执行**。部署时用一个 init Job 建表，应用实例启动只校验不建表。

### Q: 时间字段为什么用 `timestamptz` 而不是字符串？

SQLite 没有时间类型，只能存 ISO 字符串靠字典序比较；PG 有 `timestamptz`，能直接做 `expires_at > now()` 的范围比较，还能走索引。迁移时这一列必须换类型，否则比较语义还是假的。

### Q: 怎么确认 `.env` 读对了？

```python
print(bool(settings.llm_api_key), len(settings.llm_api_key), settings.llm_model)
```

只看**有没有**和**长度**，不看值。注意 `pydantic-settings` 默认不覆盖已有环境变量——如果本机 shell 里已经 export 了 `OPENAI_API_KEY` 之类的全局变量，会读到那个而不是 `.env` 里的。验证时要么清 shell 变量，要么直接解析文件。
