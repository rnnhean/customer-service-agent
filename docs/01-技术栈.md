**关于 `sse-starlette` 为什么必须单独装**：
FastAPI 自带的 `StreamingResponse` 能吐 SSE，但不管**心跳**和**断连检测**。长连接超过 60 秒、中间隔了 nginx 或公司网关，没有心跳就会被判定空闲而掐断。`EventSourceResponse` 用 `ping=15` 参数解决这个，并在客户端断开时正确触发取消。这是"聊天能流到一半断掉"这类线上问题的根因，不是可选项。

**为什么是 PostgreSQL，不是 SQLite**

三条硬理由，按分量排序：

1. **并发正确性**。本项目最核心的技术点是「退款审批 CAS 防重复」——`UPDATE approvals SET status=... WHERE apply_id=? AND status='pending'`，靠 `rowcount` 判定是否抢到。SQLite 是**全库单写者**，这条语句不会重放不是因为 CAS 有效，而是因为写操作在排队。真并发下没被验证过的正确性，等于没验证。PG 的行级锁才让这个设计站得住。
2. **部署形态**。目标形态是「一个 PG + N 个应用实例」。SQLite 是单文件：多实例共享靠 NFS，而 NFS 的文件锁语义 + WAL 组合会损坏数据库；各存各的，则会话和审批单对不上。这不是性能问题，是根本跑不起来。
3. **Checkpoint 与业务同库**。`AsyncSqliteSaver` 在多 worker 下会锁库；`AsyncPostgresSaver` 是官方生产方案，并且把 checkpoint、业务表、轨迹放同一个库，排查时一条 SQL 就能把「某个会话第 3 轮调了哪些工具、生成时引用了哪条权益」串起来。

SQLite 唯一的优势是零依赖启动，这条用一条 `docker compose up -d` 就补齐了。**面试时可以这么讲**：不是 SQLite 不好，是它的适用边界（单进程、单写者、本地）和这个项目的验收标准（多实例部署 + 并发审批）不重合。

**为什么不用 MySQL**：PG 的 JSONB、`ON CONFLICT ... DO UPDATE`、窗口函数、`pg_stat_activity` 在这几处都用得上；而本项目没有任何必须用 MySQL 的理由。

**为什么向量检索不单独引向量数据库**：权益规则最多几百条，`pgvector` 的 HNSW 索引完全够用。多引一个 Milvus / Chroma 就是多一个服务、多一套部署文档、多一个故障点，对简历项目是负收益。规模决定选型，不是越重越好。

### 1.7 中间件总览（这是面试会问的点）

「中间件」在这个项目里分两层，别混：

**A. Web 中间件（HTTP 层）**

| 中间件 | 作用 |
|---|---|
| CORS | 前端 `localhost:5180` 跨域访问后端 `:8020`（8000/8088/3001/5173 已被本机其他服务占用） |

**B. Agent 中间件（LangChain middleware，跑在模型调用前后）**

| Middleware | 本项目用途 |
|---|---|
| `SummarizationMiddleware` | **使用**：对话超过 20 条自动摘要压缩，保留最近 6 条原文 |
| `ModelCallLimitMiddleware` | **使用**：单轮最多调 N 次模型，防死循环烧钱 |
| `ToolCallLimitMiddleware` | **使用**：单轮最多调 N 次工具，同上 |
| `ToolRetryMiddleware` | **使用**：工具失败自动重试 + 指数退避 |
| `ModelRetryMiddleware` | **使用**：模型调用失败重试（429 / 超时） |

**`@ant-design/x` 值得单独讲**：
它提供 `<Bubble>`（消息气泡）、`<Sender>`（输入框带发送/停止）、`<Conversations>`（会话列表）、`<ThoughtChain>`（工具调用链展示）。其中 `<ThoughtChain>` 正好能渲染「路由到哪个 Agent → 调了哪个工具 → 结果」这条链，是把编排结构可视化的现成组件。手写这堆要处理滚动到底、流式追加、按钮状态机，很费时间。

**当前实现的架构定位要说准**：本项目是**单 Agent + 多专职节点**的 LangGraph 编排（workflow 式），**不是**多 Agent 系统。区别在：

- 每个分支节点（`benefit_rag` / `order_flow` / `refund_approval` / `complaint`）有自己的提示词和工具集，但**没有自主推理循环**——固定是「调工具 → 一次 LLM 生成 → 后置校验」，节点内不会自己决定「再调一次工具」。
- 路由由 `classify` 一次分类 + 条件边查表决定，选完不再干预。
- 节点之间靠共享 `AgentState` 传值，没有 handoff / supervisor 派活协议。

真·多 Agent 需要的是：supervisor 节点 + 每个子 Agent 各自 `create_react_agent` 子图（带 think-act-observe 多轮循环）+ 显式 handoff。那是下一阶段的事，不在当前验收范围内。**面试时按"工作流编排 + 单节点内 LLM 调用 + HITL"来讲，不要说是多 Agent**，被追问循环和 handoff 会立刻穿帮。

### 2.3 AI 流式接入

| 包 | 版本 | 角色 |
|---|---|---|
| `ai` | 7.0.163 | AI SDK 核心：`DefaultChatTransport`、`parseJsonEventStream`、UI message 协议 |
| `@ai-sdk/react` | 4.0.167 | `useChat` hook：消息状态、流式追加、abort、错误处理全包 |
| `zod` | 4.6.7 | `ai` 的 peer 依赖（`^3.25.76 || ^4.1.8`），也用来校验 data part |

**为什么用 AI SDK 而不是手写 `EventSource`**：

手写要自己处理：连接建立、分帧解析、增量拼接、中断、错误重连、多消息状态。AI SDK 把这些封装成 `useChat()`，并且它定义了一套 **UI message stream 协议**（实测协议头 `x-vercel-ai-ui-message-stream: v1`），后端只要能吐出符合协议的帧，前端就不用改。

协议帧类型（从 `ai@7.0.163` 的 `index.d.ts` 实际读取）：

```ts
type: 'text-start'   { id }
type: 'text-delta'   { id, delta }
type: 'text-end'     { id }
type: 'tool-input-available'  { toolCallId, toolName, input }
type: 'tool-output-available' { toolCallId, output }
type: 'data-<NAME>'  { data, transient? }   // 自定义数据，前端 onData 收
type: 'start' / 'finish' / 'error'
```

我们的 `approval` 事件就是自定义 data part：`{ type: 'data-approval', data: {...} }`，前端 `onData` 里接。

## 附：版本核实方法

本文所有版本号来自实际请求，不是记忆：

```bash
# PyPI
curl -s https://pypi.org/pypi/<包名>/json | node -e "...打印 info.version..."

# npm
curl -s https://registry.npmjs.org/<包名>/latest | node -e "...打印 version + engines + peerDependencies..."
```

核对过版本、**发布时间**、`requires_python` / `engines`、`peerDependencies`。
特别是下面这几个坑，是靠实测才发现的：

1. `sse-starlette 3.6.0` 要求 `python>=3.11`（不是 3.8）
2. `psycopg 3.3.8` 要求 `python>=3.9`，`psycopg-binary` 三平台都有预编译 wheel
3. `langfuse 5.2.0` 要求 `python>=3.11`
4. `ai@7` / `@ai-sdk/react@4` 要求 `node>=22`
5. `typescript-eslint@8.72.1` 与 `typescript@7.0.2` 冲突
6. `langgraph-checkpoint-postgres 3.2.0` 依赖 `langgraph-checkpoint` 4.3.x，与 `langgraph 1.2.20` 兼容
